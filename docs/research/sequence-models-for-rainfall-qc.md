# Would an LSTM or Mamba/SSM temporal component raise fault recall on daily gridded rainfall QC? (primary-source check, 2026-11-19)

**STATUS: literature check plus a read of our own result files. No training was run and no code was changed.** Every statement is tagged EVIDENCE (stated by the cited source or read in a local file), INFERENCE (my reasoning) or UNVERIFIED (could not be checked at the owning document). Searches used generic technical terms only. Some pages could not be fully read (noted where it matters): the Hubbard et al. PDF and the Sciuto et al. page returned HTTP 403, so those two are cited from search snippets and the El Hachem et al. description only.

## Summary and recommendation

**Honest answer: swapping the GRU for an LSTM or Mamba is unlikely to raise fault recall in the current system, and I would not do it first.** Four reasons, in order of strength:

1. **The score cannot see zeroed faults, whatever the network.** A zeroed day is a dry observation, and the temporal/spatial score for a dry observation is `-log P(dry)` (`qc/models.py`, `surprise`). At the 1.0 budget the temporal threshold is 7.12 nats, so a zero is flagged only if the model predicts P(wet) >= 0.9992. That almost never holds for daily rain. This is a property of the scoring function, not of GRU vs LSTM vs Mamba (INFERENCE from local code and `comparison_s42.json`).
2. **Scale and zeroed faults need information the temporal component is not given.** It sees only the cell's own previous 30 days (never the scored day or neighbours). One day's value that is a plausible-looking multiple of normal, or a zero in a rainy spell, is only identifiable against same-day neighbours or physical context (INFERENCE; supported by El Hachem et al. 2022, which detected daily false zeros using neighbour kriging).
3. **The headroom the temporal part could add is small in our own numbers.** Fused recall is 0.436 and rules alone 0.429 at the 1.0 budget, so spatial + temporal + slow + neighbour-baseline together add 0.007 absolute (EVIDENCE: `comparison_s42.json`). The owner's own decision rule asks for >= 0.02 absolute gain (`base.yaml`, `architecture.min_recall_gain`).
4. **The published case for Mamba does not cover this regime.** The Mamba paper tests language, DNA, audio and two synthetic tasks, with sequences up to 1M tokens, and none of that is short, noisy, zero-inflated series with a 30-step context. Independent time-series papers report mixed results for plain Mamba (Section 3).

Also, the recall metric may cap what any model can reach: `CHANGED_MM = 0.001 mm` means fringe cells of a footprint fault with weight near 0 are labelled as faults, and 95% of labelled cell-days belong to footprint events (27,718 of 29,098). Even spikes of at least +57 mm at the centre only reach 0.22 recall. That points at the benchmark's label definition, not at model capacity (INFERENCE; test in experiment 1 below).

Ranked plan is in "What to try first". Cheapest, most informative: recompute recall by detectability (footprint weight and size of change), then add signed neighbour-residual features to the fusion, then longer training of the existing GRU, and only then LSTM/Mamba.

## 0. What the temporal component sees and predicts (local files, EVIDENCE)

- `qc/models.py` `TemporalGRU`: a one-direction `nn.GRU(2, 64)` over two channels per day (normalised `log1p(mm)/scale` and a valid flag), 30 days, oldest first. Its last hidden state is concatenated with 4 static features (sin/cos day of year, log1p climatology of that cell and day, log1p heavy-rain threshold), then a 64-unit dense layer and a 3-output head: logit of P(wet), Gamma shape, Gamma scale (zero-inflated Gamma).
- `qc/batches.py` `history`: rows `t-30 .. t-1` of the same cell; "the scored day itself is never included"; no neighbour cells.
- `qc/trained.py`: inputs come from the block corrupted on the fly with the seen fault settings; the target is the clean value of the same cell-day; loss is the zero-inflated Gamma NLL on the clean value. The fault-supervised term (`fault_term`) exists in code but runs only if `train.fault_weight > 0`; `base.yaml` does not set it, so it is off (EVIDENCE: `year_steps` reads `tr.get("fault_weight", 0.0)`).
- Scoring (`surprise`): for a dry observation (<= 0.1 mm), score = `-log P(dry)`; for a wet one, minus the log of the smaller tail probability. Per-component thresholds at budget 1.0: temporal 7.12, spatial 7.77, rules 0.38 (EVIDENCE: `comparison_s42.json`).
- Training: 3 epochs x 62 years x 40 steps = 7,440 gradient steps. The per-year loss in `train_log_temporal_s42.json` runs from 0.24 (first year) to about -0.15 at the end, minimum -0.28. Years differ in wetness and corruption, so these per-year values are not a clean convergence curve; whether the model has converged cannot be read from the log (INFERENCE). Batch size comes from `compute.batch_size` for the `single-gpu` profile; I did not find the number (UNVERIFIED).
- Fusion (`qc/fusion.py`): takes one scalar score per component per cell-day (names `rules`, `slow`, `neighbour_baseline`, `spatial`, `temporal`, `plain_gru`). I did not read whether the neighbour-baseline score keeps the sign of the residual; if each component is a non-negative score, the fusion cannot see "observed far below expected" as distinct from "far above" (UNVERIFIED; check `qc/scoring.py`).
- Recall at the 1.0 budget, val 2016-2017, seen settings (cell-day recall; EVIDENCE: `comparison_s42.json`, `by_budget["1.0"]["by_kind"]`):

| component | overall | stuck | phantom | combination | spike | scale | drift | zeroed |
|---|---|---|---|---|---|---|---|---|
| fusion_logistic | 0.436 | 0.83 | 0.79 | 0.50 | 0.22 | 0.03 | 0.01 | 0.00 |
| rules | 0.429 | 0.82 | 0.79 | 0.50 | 0.20 | 0.01 | 0.00 | 0.00 |
| slow | 0.091 | 0.05 | 0.02 | 0.18 | 0.09 | 0.00 | 0.00 | 0.00 |
| neighbour_baseline | 0.067 | 0.06 | 0.01 | 0.11 | 0.21 | 0.01 | 0.01 | 0.01 |

**Important:** the neighbour-based components (spatial, neighbour_baseline) also score about 0 on scale, drift and zeroed. So the missing information is not simply "neighbours": the current neighbour scores do not catch these faults either. Reasons visible in the fault generator (`qc/faults.py`, EVIDENCE) and the metric:

- Half of faults have a footprint of radius 1.5-4 cells with weight `(1 - d/r)^2`; corrupted = orig + w*(faulty - orig). A footprint zeroed fault is therefore a smooth multiplicative reduction `orig*(1-w)`, and neighbours outside the 2-cell hidden disc are partly corrupted too (INFERENCE: this blunts neighbour residuals).
- A cell-day is labelled if `|new - orig| > 0.001 mm`. For the fringe of a footprint, w can be near 0 and the change tiny, but the cell-day still counts as a fault. In the fused result, 27,718 of 29,098 fault cell-days come from footprint events and 1,380 from single-cell events (EVIDENCE: `by_radius`). Cell-day recall is dominated by footprint fringes (INFERENCE).
- Spike adds at least `10 + 190*0.25 = 57.5 mm` at the centre, yet recall is 0.22 for every method. That cannot be a capacity limit; most labelled spike cell-days must carry a small blended change (INFERENCE).
- Scale applied to a dry day changes nothing (0 x f = 0) and is not labelled; scale of a small wet value (e.g. 0.5 mm x 3) stays within normal day-to-day variation (INFERENCE).
- Drift ramps from 0 to the full error over 21-60 days, so the early days differ from clean by a few percent and cannot be flagged day by day by any method (INFERENCE). Event-level recall (fused 0.57 vs cell-day 0.44; temporal 0.29 event vs 0.015 cell-day) is the fairer measure for drift and slow faults.

## 1. Published evidence: sequence models and neighbour/non-neural QC for precipitation

**Established non-neural practice (rules + neighbours)**

- GHCN-Daily QC (Durre, Menne, Gleason, Houston, Vose 2010, J. Appl. Meteor. Climatol. 49, 1615-1633; https://ncei.noaa.gov/pub/data/ghcn/daily/papers/durre-menne-etal2010.pdf). For precipitation it uses duplicate, streak, frequent-value, gap, climatological-outlier (>= 9 x the 95th percentile of nonzero values, 29-day window) and spatial corroboration (neighbours within 75 km, 3 to 7 of them, lags -1, 0, +1 day). The paper says a z-score check over-flags skewed precipitation, so z-scores are used for temperature only. EVIDENCE as extracted in `docs/research/operational-rainfall-qc-primary-sources.md` (that note marks several thresholds UNVERIFIED; I did not re-read the paper).
- Hubbard, Goddard, Sorensen, Wells, Wilhite 2005 (J. Atmos. Oceanic Technol.; citation from memory, UNVERIFIED): spatial regression against the best-fitting neighbours with a confidence interval, reported by search snippet to outperform threshold, step-change and persistence tests, and to find precipitation harder than temperature. The PDF returned HTTP 403, so this is UNVERIFIED at the owning document. The HESS paper below describes it as flagging values outside +-3 SD of the long-term mean that also differ from a spatial-regression estimate (EVIDENCE via El Hachem et al.).
- El Hachem, Seidel, Imbery, Junghänel, Bárdossy 2022, "Technical Note: Space-time statistical quality control of extreme precipitation observations", HESS 26, 6137-6146; https://hess.copernicus.org/articles/26/6137/2022/hess-26-6137-2022.html. Box-Cox transform, leave-one-out kriging from the 30 nearest stations, flag when observed vs kriged estimate exceeds 3 criteria units, repeated across aggregations; flagged values checked against radar and discharge. In a 20-station test, decreasing values caught about 60% of hourly and 94% of daily false zeros. Limitations they state: neighbouring false highs cause false flags, and frontal events with dry neighbours can be misflagged. EVIDENCE. This is the closest published match to our "zeroed" and "scale" gap, and it is neighbour-based, not sequence-based.
- Sciuto, Bonaccorso, Cancelliere, Rossi 2009 (J. Hydrology; Sicily): neural networks give confidence intervals from same-time observations at reference stations, because daily zeros and high variability make station-only historical intervals unreliable; reported >80% of data validated. UNVERIFIED (page returned 403; from a search snippet). Moslemi & Joksimovic (HIC 2018) report a similar neighbour-based network (about 97% validated at 95% intervals; snippet, UNVERIFIED). Both use contemporaneous neighbours as inputs, not own-history sequences.

**Sequence models on rainfall or gauge QC**

- Schulz & Niemann 2025, "Automatic Quality Control of Rain Gauges Using Machine Learning and Generalization to a Catchment" (IAHR library, http://www.iahr.org/library/infor?pid=37771). Sub-daily, highly imbalanced gauge data over a 1,500 km2 catchment. Random forest vs CNN-LSTM, single-station vs generalised models; the generalised random forest was best, and the authors conclude simpler models and catchment-scale models are preferable. EVIDENCE (abstract only; per-model numbers not seen). This is a reported case where the simpler model beat the CNN-LSTM on gauge QC.
- Wang & Zhang 2024, "Using LSTM to merge precipitation data over mountainous area in Sierra Nevada", arXiv:2404.10135. The LSTM-merged product "notably underestimated" gauge observations and often gave near-zero values. EVIDENCE (abstract). Relevant to zero-inflation collapse in a plain LSTM, not to QC.
- Prior notes in this repo: LSTM autoencoders for weather-station QC (Spohn et al. 2026; Supriyatna et al. 2026) are for non-rainfall variables (`docs/research/prior-work-precipitation-qc-positioning.md`). A UK Met Office poster on a graph neural network emulating manual daily-rainfall QC reported that it overpredicts anomalies (RMetS Early Career conference 2026; search snippet only, UNVERIFIED).
- Mamba/SSM on precipitation: I found Mamba used for radar/satellite nowcasting and meteorological downscaling (MambaRain, arXiv 2605.14606; MambaDS; WSSM arXiv 2501.11238), all from search snippets (UNVERIFIED), none for gauge or gridded-rainfall QC and none using a zero-inflated likelihood. Search found no Mamba/S4 paper on zero-inflated or intermittent rainfall series QC. This is a negative search result, not proof of absence.
- The earlier arXiv review in this repo reached the same gap for rainfall QC with injected errors (`docs/research/slr-weather-anomaly-detection-models.md`, marked provisional).

## 2. Does a sequence model help for scale, zeroed and drift? Information needed per fault kind

All of this section is INFERENCE unless a source is named.

| fault | what identifies it | what our temporal GRU sees | would a better sequence model help? | cheaper alternatives |
|---|---|---|---|---|
| zeroed | observed 0 while same-day neighbours (and the cell's forecast) are wet | own past 30 days only; scored by `-log P(dry)` | No. Bounded score (threshold 7.12 nats needs P(wet) >= 0.9992); the day's neighbours are absent | neighbour residual on the expectation (not the tail probability); El Hachem et al. false-zero test |
| scale (x or /) | magnitude vs neighbours and vs climatology on that day | own past only; a x1.5-x10 or /f value of a normal day is within normal variability | No for single days. A longer run (1-7 days) of a consistent ratio to neighbours is visible only against neighbours | cell/neighbour log-ratio, multi-day aggregation, per-cell climatology z-score in log space |
| drift | slow change of the cell/neighbour ratio or bias | 30 days; ramp is 21-60 days and near zero at the start | Marginally; a state that integrates over 60-90 days could help, but a plain CUSUM/change-point on the neighbour ratio is simpler and exact | CUSUM or Page-Hinkley on log(cell/neighbour-ring) totals; the existing `slow` (30/90-day totals) gets 0.00 so check its threshold and window |
| spike | magnitude vs own distribution and neighbours | own past; works at 0.16 | Little. Rules and neighbours already reach 0.2 | longer training; fault-supervised term already in code |
| stuck, phantom | exact repeats, drizzle on dry days | own past, but ZIG on a continuous Gamma cannot represent "exactly equal" | Not through the likelihood; rules already 0.82 and 0.79 | keep rules |

- A change-point test is the textbook tool for drift and is not an architecture issue. I did not retrieve a specific rainfall-QC paper for CUSUM on neighbour ratios; the principle is UNVERIFIED for this benchmark and should be tested, not assumed.
- Per-cell climatology z-score: Durre et al. state a z-score over-flags skewed precipitation, so a plain z-score on mm is a poor choice. A z-score on `log1p` or the gamma tail, per day-of-year window, is what the GRU's static features approximate (EVIDENCE for the Durre statement; INFERENCE for the rest).
- "Proper zero-inflated likelihood": we already use it. It is the right likelihood for the generative model, but the surprise made from it has a hard ceiling for dry observations. To flag "zero when wet was expected", use a directional statistic (expected wetness or expected amount given neighbours minus observed), not the tail probability of the dry outcome.
- "Train longer": plausible for spike and combination; will not fix zeroed (bound above). The 3 x 40 x 62 step budget is small, so longer training is a legitimate check but with a clear prediction below.

## 3. Mamba / S4 vs LSTM / GRU / Transformer for anomaly detection: claims, tests, failure modes

- Original claims. **S4**: Gu, Goel, Ré 2021, "Efficiently Modeling Long Sequences with Structured State Spaces", arXiv:2111.00396. Targets sequences of 10,000+ steps; 91% on sequential CIFAR-10; state of the art on every Long Range Arena task including Path-X (length 16k); generation about 60x faster. EVIDENCE (abstract). **Mamba**: Gu & Dao 2023, "Mamba: Linear-Time Sequence Modeling with Selective State Spaces", arXiv:2312.00752. Making SSM parameters input-dependent ("selection") removes the efficient convolution form, so a hardware-aware scan is used. Tested on synthetic Selective Copying and Induction Heads, language (Mamba-3B matches Transformers twice its size; scaling laws up to 1B), DNA (up to 1M-token context) and audio waveforms; 5x higher inference throughput than Transformers. EVIDENCE (read from the paper text).
- What the Mamba paper does not test, EVIDENCE from the text: no time-series forecasting or anomaly detection task, no zero-inflated data. Its own discussion says evaluation is limited to small model sizes (Section 5, Scaling). It notes real-valued SSMs work for discrete data while complex-valued states help continuous modalities such as audio (Section 3.5), so even the authors treat the continuous/discrete distinction as open for the architecture. It states that LTI SSMs (S4-style) "have fundamental limitations in modeling certain types of data" such as selective copying, which is why selectivity was added.
- Mamba's headline strengths (very long context, linear scaling, selective memory) address 100k-token problems. Our input is 30 steps of 2 channels. At that length attention, GRU and LSTM are all cheap and there is no long-context bottleneck to remove (INFERENCE).
- Expressivity limits. Merrill et al. 2024, "The Illusion of State in State-Space Models", arXiv:2404.08819: SSMs including Mamba are in the same complexity class as Transformers (TC0), cannot do simple state tracking such as permutation composition, and Mamba-style models struggled experimentally. EVIDENCE (abstract; author list from memory, UNVERIFIED). Our faults are not state-tracking problems, so this is a caution about expecting extra reasoning from SSMs, not a direct failure of our case.
- Benchmarks of anomaly detection models.
  - TimeSeAD (Wagner, Michels, Schulz, Nair, Rudolph, Kloft 2023, TMLR; https://mlanthology.org/tmlr/2023/wagner2023tmlr-timesead): 28 deep methods on 21 datasets. In the full-text copy I could read (first 100,000 of 152,623 characters), Section 4.4 says "no single method dominates" and older, less complex methods such as LSTM-AE did well on SMD; Section 6 says modern approaches often struggle to reach the performance of older methods; the authors caution results depend on a fixed training budget and reduced hyperparameter grids. EVIDENCE for those statements; I did not read the final 52,623 characters. Mamba is not in that benchmark (it predates the Mamba papers' spread; INFERENCE).
  - Kim et al. 2022, "Towards a Rigorous Evaluation of Time-series Anomaly Detection", arXiv:2109.05257 (authors UNVERIFIED): point-adjusted scoring can make a random anomaly score look state of the art, and an untrained model performs about as well as published methods even without point adjustment. EVIDENCE (abstract). Relevance: gains of a few points from a new sequence architecture need seed variance and an untrained baseline beside them. We already have an `untrained` run folder.
  - Zeng et al. 2022, "Are Transformers Effective for Time Series Forecasting?", arXiv:2205.13504: single-layer linear models beat Transformer forecasters on nine datasets, and the authors suggest examining other tasks including anomaly detection. EVIDENCE (abstract; forecasting, not QC).
- Mamba in time-series papers.
  - Wang et al. 2024, "Is Mamba Effective for Time Series Forecasting?" (S-Mamba), arXiv:2403.11144: claims lower GPU memory and training time and leading performance on 13 datasets (authors' own claim; I did not verify the numbers).
  - Xu et al. 2024, "SST: Multi-Scale Hybrid Mamba-Transformer Experts for Time Series Forecasting", arXiv:2404.14757: "naively stacking Mamba and Transformer layers ... is suboptimal for time series forecasting". EVIDENCE (abstract). A search snippet said naive stacking fails to beat DLinear; the abstract does not say so, UNVERIFIED.
  - Chen & Sun 2026, "DMamba", arXiv:2602.09081: "existing Mamba-based architectures often struggle with datasets characterized by non-stationary patterns". EVIDENCE (abstract). Rainfall under a monsoon regime is strongly non-stationary (INFERENCE).
  - MambaTS reportedly found direct application of Mamba to long-term forecasting gave no gain over Transformers (search snippet, UNVERIFIED; not opened).
  - Anomaly-detection adaptations (MAAT arXiv:2502.07858, Fourier-KAN-Mamba arXiv:2511.15083, DeMa arXiv:2601.05527, AnoMamba IJCAI 2026) are described in snippets as needing extra modules because plain Mamba is suboptimal for multivariate series (UNVERIFIED; abstracts not opened). They are evaluated on standard benchmarks, not rainfall.
  - Hu et al. 2024, arXiv:2409.03231: Mamba ranked among the top of 11 baselines on dynamical-system operator learning (EVIDENCE, abstract). This is a positive case, on smooth dynamics.
- Net (INFERENCE): the independent literature supports "Mamba is competitive in some forecasting settings, often needs added structure, and shows no consistent advantage over simpler recurrent or linear baselines"; none of it is for zero-inflated gauge or gridded QC.

## 4. Practical cost on one RTX A6000-class GPU

- Data size (INFERENCE from the config): 4,964 cells x 62 years x 365 days = about 112 million cell-days, about 0.45 GB as float32 for the whole 1951-2012 training field. It fits in 48 GB VRAM many times over. A 30-day, 2-channel window is 240 bytes; a batch of 16,384 windows is about 4 MB. Memory is not the constraint for any of the three models.
- Our current temporal model is tiny: GRU hidden 64 over 30 steps. LSTM has four gates instead of three, so a hidden-64 LSTM is about one third larger in parameters and a bit slower per step; both use the same cuDNN recurrent kernels in PyTorch (INFERENCE, not benchmarked here). I did not measure wall time; the user reports a few minutes for 7,440 steps. A 20x longer run is about an hour or two under linear scaling (INFERENCE, not measured, and the batch size and data loading are not known to me).
- Mamba's claimed efficiency (4-5x inference throughput, 20-40x faster scan than a naive PyTorch scan, faster than FlashAttention-2 beyond length 2K; EVIDENCE: Mamba paper Section 4.5) is for long sequences. At length 30 the fused scan has little to speed up (INFERENCE). I found no benchmark of Mamba vs GRU/LSTM at L=30 and a few thousand hidden units or fewer (UNVERIFIED).
- **Windows.** The official README (https://github.com/state-spaces/mamba, fetched from the repository) lists "Linux", "Python 3.10+", "PyTorch 1.12+" as core requirements, and "NVIDIA GPU" and "CUDA 11.6+" for the `selective_scan_cuda` build; it also says `--no-build-isolation` is required for CUDA builds, that the default install skips the CUDA extension, and that AMD uses ROCm. It does not mention Windows. EVIDENCE.
  - Issue #644 "Guide to Install on Windows" is open, with no maintainer reply on the page; users suggest WSL2 and point to another issue about native Windows support (https://github.com/state-spaces/mamba/issues/644). Issue #662 (Windows, triton missing, --no-build-isolation failure) was closed by its author after switching to VS Code with WSL (https://github.com/state-spaces/mamba/issues/662). EVIDENCE for what the threads say; neither is a maintainer-accepted native-Windows fix. A community post says Triton supports only Linux (search snippet, UNVERIFIED).
  - In `mamba_simple.py` the causal-conv and Triton state-update imports are wrapped in `try/except ImportError`, but `selective_scan_fn` is imported unguarded, so the core scan path has no fallback visible in that file (EVIDENCE for the file; whether `selective_scan_interface` falls back internally is UNVERIFIED).
  - Practical path (INFERENCE): the repo already has `kaggle_sync.py` (Linux notebook runs), where the official package may build; or WSL2 on this machine; or a 30-step pure-PyTorch selective scan written in the project (a 30-iteration loop is cheap), which avoids the dependency. Whether mamba-ssm builds on your Kaggle image or WSL2 is UNVERIFIED.

## What to try first (ranked, cheapest first)

Every experiment uses the existing frozen validation benchmark, budget 1.0, the three seeds in `train.seeds`, and the owner's gain rule (>= 0.02 absolute fused recall, `architecture.min_recall_gain`), so that a change is judged against seed spread and the untrained baseline.

1. **Detectability ceiling (no training, CPU, minutes).** Recompute recall per kind in bins of footprint weight (w >= 0.5, 0.1-0.5, < 0.1) and of change size (`|new-orig|` >= 5 mm or >= 50% of the original), and also at event level. *Prediction:* recall for spike, scale and zeroed rises sharply in the high-weight bin (spike toward 0.8-1.0 at weight >= 0.5) and is near 0 in the lowest bin. *Success of the explanation:* spike recall in high-weight bins is above 0.7, meaning the 0.22 overall is mostly a label-definition effect. *Failure:* spike recall stays near 0.2 even at weight >= 0.5, which would mean the detectors themselves are weak and the benchmark is not the main limit.
2. **Zeroed score bound (no training).** For all labelled zeroed cell-days, take the predicted P(wet) from the saved temporal and spatial heads and compute `-log P(dry)`; report the share that could ever reach the 1.0-budget thresholds (7.12, 7.77). *Prediction:* under 5% reach it, in line with recall 0.00. *Failure:* a large share reach it, then the bound argument is wrong and the problem is elsewhere (for example the fusion).
3. **Directional neighbour features in the fusion (no new network training).** Add, per cell-day, signed log-ratio of observed to the spatial net's expected amount, the spatial net's predicted P(wet) beside the observed wet/dry state, and the neighbour baseline's signed residual, and refit the logistic fusion on the same fit years. This is the El Hachem et al. idea (neighbour estimate vs observed) in the fusion's own terms. *Prediction:* zeroed and scale recall each rise to at least 0.10 at the same false-alert budget, with fused overall up by >= 0.02. *Failure:* zeroed and scale stay under 0.03 after the fit, which says the benchmark's blended footprints leave nothing to detect and the next move is a metric/benchmark change, not a model change.
4. **Change-point statistic for drift and slow scale (cheap, no network).** CUSUM or Page-Hinkley on `log(cell total / neighbour-ring total)` over 7 and 14 days, added as a component. Check also why `slow` (30/90-day totals) has drift recall 0.00. *Prediction:* drift event recall (not cell-day) reaches at least 0.3 at the same budget, with detection delay of a few weeks. *Failure:* under 0.1, which would indicate that the drift sizes sampled (1.3-2.5x at the end of the ramp) are too small to separate from rain variability at this FA budget.
5. **Train the existing GRU longer, with and without the fault-supervised term (hours of GPU).** 10x and 30x the current 7,440 steps; second variant with `train.fault_weight` > 0 (code path exists). *Prediction:* temporal-alone recall rises mainly on spike and combination; zeroed stays near 0 (bound in experiment 2); the fused gain over the current fusion is under 0.02. *Success:* fused up by >= 0.02. *Failure:* temporal-alone below 0.05 after 30x, which would end the case for "just under-trained". If the fault-supervised variant rises while the likelihood-only variant does not, the limit is the objective, not the model.
6. **LSTM drop-in (two-line change, same budget, three seeds).** *Prediction:* no difference from the GRU outside seed spread (fused change < 0.01). *Success:* >= 0.02 over GRU in every seed. I expect failure for the reasons in the summary.
7. **Mamba/SSM, only if a precondition holds.** Precondition: show first with the GRU that longer history helps (30 -> 90 -> 365 days, `history_days` is 90 today) and that the GRU degrades or saturates. Then try a small selective SSM, as a pure-PyTorch scan if `mamba-ssm` is hard to build here (Section 4). *Prediction:* no gain at 30 days; at best a small gain for drift at 365 days that a change-point test (experiment 4) already delivers more cheaply. *Failure:* no precondition met, in which case Mamba should not be run.

## What this document does not settle

- No result here says Mamba or LSTM cannot work for gridded rainfall QC; it says there is no published evidence that they help, and our own numbers point to the score definition, the label definition and missing neighbour signals as the limits.
- I did not train anything, so every "prediction" above is a hypothesis to test, not a result.
- UNVERIFIED items: Hubbard et al. 2005 details, Sciuto et al. 2009, Moslemi & Joksimovic 2018, the Met Office poster, the AD-specific Mamba papers (MAAT, Fourier-KAN-Mamba, DeMa, AnoMamba), MambaTS, the fusion's use of signed scores, whether `mamba-ssm` builds on WSL2 or Kaggle, and wall-clock times.
